# 为什么实时数据必须有界

直播消息流没有天然终点。只要把每条消息保存在数组、Map 或 DOM 中，内存就会随直播时长
增长。即使单条消息很小，长时间运行和多路播放也会把它放大成稳定性问题。

LiveFlow 因此把“有界”视为 interface 的一部分，而不是实现优化。

## 上限覆盖哪些资源

每个引擎都必须限制：

- 等待队列；
- 同时可见项目；
- DOM 节点池；
- listener、计时器和实例注册；
- 每条消息的文本、节点、身份与 metadata；
- 单位时间接收和显示数量；
- 每帧测量与挂载工作量。

这些上限共同约束内存和主线程成本。只限制队列但允许无限 DOM，或只限制 DOM 但保存全部
历史消息，都不能形成真正的资源平台。

## 过载时为什么丢弃

实时内容的价值随时间快速下降。系统已经落后时继续积累旧消息，只会让延迟越来越大。LiveFlow
先丢弃过期内容，再保留高优先级结构消息，最后对普通消息执行稳定丢弃。

丢弃是可观察行为：metrics 和诊断会记录发生了什么。引擎不会把扩大队列当作恢复手段，也不
会为了“补完历史”突然加速大量动画。

## 如何判断资源达到平台

压力测试不以“处理了多少条消息”为唯一结果。更重要的是：

- 队列深度始终不超过配置；
- 可见项目和节点池达到稳定上限；
- 输入继续增长时 dropped 增长，而内存不线性增长；
- `destroy()` 后计时器、RAF、listener、节点和预算 grant 归零。

因此 soak 输入使用合成数据并持续远超显示能力，验证的是资源曲线，而不是特定平台的消息
格式。
