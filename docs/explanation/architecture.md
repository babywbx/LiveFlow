# 为什么 LiveFlow 使用独立引擎和适配器

LiveFlow 把直播页面拆成三个彼此独立的引擎：

- 连续性引擎处理媒体 generation、尾距、卡顿和换源；
- 弹幕引擎处理高频、短生命周期的滚动消息；
- 实时事件引擎处理低频、结构化、视觉成本较高的事件卡。

播放器和 DOM 都位于适配器 seam。核心引擎只依赖小型 interface，不创建播放器实例，也不
理解媒体地址来自哪个平台。

## 为什么连续性核心不绑定播放器

连续性决策只需要少量事实：当前播放时间、前向缓冲、直播尾距、卡顿时间和媒体事件。把具体
播放器放进核心会带来三个问题：

1. 核心入口会被迫下载播放器运行时；
2. 播放器生命周期会与业务页面生命周期耦合；
3. 同一套恢复算法无法在原生 video、自定义播放器和测试替身之间复用。

`LivePlayerAdapter` 把这些差异压在一个 seam 后面。连续性模块因此可以保持零运行时依赖，
调用方也可以只在用户真正开始播放时动态加载所需 adapter。

## 为什么弹幕和事件卡使用不同调度器

普通弹幕数量高、单条价值低，目标是稳定吞吐和避免碰撞。事件卡数量低、视觉成本高，目标是
去重、优先级、展示时长和跨实例预算。让两者共用一个队列会使高频弹幕堵住重要事件，或者让
高成本事件卡耗尽滚动轨道预算。

两个引擎可以接收同一时刻的数据，但各自拥有队列、过载策略和生命周期。这样任何一层过载都
不会阻塞另一层。

## 为什么全局预算不是模块级单例

多路播放时，单实例上限无法约束页面总成本。LiveFlow 提供显式创建的预算协调器，由页面把
同一个实例传给各播放位。

显式协调器有三个好处：

- 页面可以决定哪些播放位共享预算；
- 测试可以独立创建和销毁预算域；
- 页面卸载时可以确认所有注册和 grant 已释放。

模块级单例会跨页面、测试和热更新残留状态，也无法表达两个互不相关的播放网格。

## 平台职责留在哪里

LiveFlow 不获取直播地址、不解析签名、不连接平台弹幕协议，也不判断主播是否在线。调用方
负责把平台数据投影成通用 source、弹幕消息和结构化事件。LiveFlow 只处理投影后的浏览器侧
生命周期。
